# 静默失效图鉴 —— 「机制在、生产零生效」

> **这不是 session 记录,是一份长期台账。** 它收的是这个仓**反复撞见的同一族缺陷**:
> 机制写好了、配置项也在、测试全绿,而它在生产上一次都没生效过 —— 并且**没有任何红灯**。
>
> 为什么值得单独一份:这一族的每一个实例,当时都是"靠撞"发现的,不是靠计划。
> 写下形状之后,下一次可以靠**认**——甚至靠**闸**。
>
> 每加一条,请一并回答:**怎么抓**(最好是一条可自动化的判据)。
> 只描述现象而没有抓法的条目会退化成读物。

---

## 判据:什么算这一族

三条同时成立:

1. **声明面存在** —— 有配置项 / 有字段 / 有函数 / 契约里写着;
2. **消费面缺席或错位** —— 没人读它,或读的是另一个东西;
3. **两边都不报错** —— tsc 绿、测试绿、运行不抛,症状伪装成别的东西。

第 3 条是要害。会报错的缺陷不属于这一族 —— 它们一次就被发现了。

## 图鉴

### S-1 · 声明了但没有消费者

**形状**:schema / prompt / 座位表里出现一个字段,引擎里没人读它。

**为什么没红灯**:zod 容忍未知字段;prompt 是字符串;座位被 auto-assign 派了模型、被起跑自检查了凭证——**看起来全都在动**。

**本仓实例**
- `max_retry` / `on_failure` / `fallback` 三个 node 字段零消费者。
- `postcondition` 被两个 conductor prompt 反复明示,而引擎从不检查 —— 更坏的是它**把 conductor 从真的会跑的 command / judge 节点那条路上引开了**(写了个验证的样子)。
- `escalation` 座位纯装饰:auto-assign 给它派模型,引擎读的却是 `OMD_CONDUCTOR_ESCALATION_MODEL`。
- `gate.thinking` 写在座位登记表里,而 `llm-judge` 根本不传 `thinkingLevel`(2026-08-01)。
- `verifier.thinkingLevel` 硬编码 `'xhigh'`,座位里写什么都到不了调用上(同上)。

**怎么抓**:`src/harness/empty-knobs.test.ts`
- 「明示即承诺」:conductor prompt 里出现的每个 node 字段,必须登记 `file:line` 级消费点。
- 「座位即承诺」:`ALL_SEATS` 每个座位必须有解析点。

**这道闸抓不到的**:① 见 S-2 —— 它只问"有没有人解析",不问"解析出来的东西有没有被用在它该用的地方";
② 见 S-11 —— 也不问"解析它的那个文件本身有没有人调"(`dream` 座位就是栽在这里,由可达性闸补上)。

### S-2 · 坐标被人用 ≠ 它代表的机制在跑

**形状**:一个配置项**确实被读了**,但读它的是另一个用途;它本来该驱动的那道机制从没启动。

**为什么没红灯**:所有"有没有人读"的闸都会绿。

**本仓实例**(2026-08-01,最贵的一条)
- `verifier` 座位在 MCP 路径上**确实被解析** —— 被借去组 `stampPools.strong` 那个池。
  于是「座位自检 16/16 ✓」与「跨模型终审闸一次都没跑过」**同时成立**。
  `config.verifier` 只在 `tui.ts` 里被设过;`tools/dag-tools.ts` 里那句
  「MCP 路径无 verifier」的注释,就是当年照着这个事实改下游判据时留下的。
- `judgeModel` 从不被装配层给出 → 引擎落回 `?? config.conductorModel`,
  于是「判这一轮收敛没有」的那一发一直**骑在 conductor 座上**,改 judge 座位不生效。

**怎么抓**:`src/mcp/seat-wiring.test.ts`
判据取**引擎真收到的 config**,不是"装配层有没有那行代码"——后者是看着像验了。
> 加一道新的引擎能力时问自己:**它的开关在哪条路径上被真的传进去了?** 两条路径都传了吗?

### S-3 · 机制写好了,但默认关着 / 只挂在一条路上

**形状**:能力完整、注释详尽、甚至有测试,而生产从来没吃到。

**为什么没红灯**:它是"可选增强",不给就是不给。

**本仓实例**
- `warmThenFanout`(暖发共享前缀)早就写好,默认 `false`,**只有两个 eval oracle 开过**。
- `createDagRecorder` 只挂在 TUI 侧的 `/cg /audit /iterate` 上,MCP 这条从没接过 →
  生产路径上那个库恒空,「一次 goal 多少钱」与「兄弟节点吃到多少缓存」两个问题都没有数据源。
- auto-compaction:老 `createAgentSession` 自带,搬到低层循环时弄丢,只留"到线就停"(2026-08-01)。
- **R2 的 run 级隔离(独立 worktree + 分支)—— 这一条 2026-08-06 量到了硬读数**:
  `branchStrategy` 只挂在 `dag_goal` **一个入口**上(其余五个入口连这个旋钮都没有),缺省 `head`。
  实测 `git worktree list` 没有一个 `omd/run/*`、`git branch --list 'omd/run/*'` **0 条**
  —— **从来没有被用过一次**。它同时把 backlog D1(「跑坏了怎么回滚」)一直卡在开着的状态:
  D1 的问法预设了"产出落在一个分支上",而生产上从来没有那个分支。
  > **这一条与上面三条的区别在于它有读数。** S-3 此前只有"没人用"的印象;这次是
  > **盘上数得出来的 0**。找同类的办法也一并记下:**问这个机制在盘上会留下什么痕迹,
  > 然后去数那个痕迹** —— worktree 留目录、分支留 ref、缓存留文件。数不出痕迹的机制,
  > 「有没有人用」就永远只能靠印象。
- **D-13 的 prototype 隔离 worktree —— 这一条比"零痕迹"再强一格:它在 import 图上没有可达的调用者**
  (2026-08-06,查 backlog S4 的前置时撞到)。那段代码住在 `pathfinder/dispatch.ts` 的
  `case 'prototype'` 里,而唯一调 `dispatchTicket` 的 `dispatchFrontier` **只自动派 research 票** ——
  注释写着 prototype「仅 reported 给 UI 由人显式触发」,**而那个触发口从来没建过**。
  prototype 票实际走的是 `readyRegion → path_deliver → detached solve`,那条路不传
  `branchStrategy` → 缺省 `head` → **直接写主树**。
  **「沙盒 spike,试验码不污主树」这句话在生产上是反的。**
  > **于是找同类的办法扩一条:除了数盘上的痕迹,还可以数它有没有调用者。**
  > 前者答"没人用",后者答"**没人用得了**" —— 后一个是结构事实,不受采样期影响。
  >
  > ⚠ **但这条办法机械化不了,量过了**(2026-08-06):按「导出函数在别的生产文件里没被引用」
  > 扫全仓,**613 个里报 213 个(35%)** —— 做不成闸。噪声的主因是**有意为之**的那一类:
  > 函数在自己文件内被用、只为测试而 export(`readyRegion` 的注释就写着「生产只有本文件消费」)。
  > **更要紧的是它抓不到上面这条实例**:D-13 那个洞不是"函数没人调",是 `dispatchTicket`
  > **有**调用者、而那个调用者 `if (t.type === 'research')` 把 prototype 滤掉了。
  > 看出这一点要**读调用方的条件**,不是数引用次数。
  > → **这一格没有闸,只有提问纪律**(同 S-3 本身):怀疑一个机制没在跑时,
  > **顺着唯一的调用者往上读它的判断条件**,别停在"有没有人 import 它"。
  > ⚠ 修法**不是把 default 翻成隔离**:隔离 worktree 是 HEAD 那一版的干净 checkout,
  > **看不见未提交的活**(同日查实)。带着未提交改动跑 spike,改成隔离只会让它看不见自己的活。
  > 今天先把这件事**在回话里说出来**(闸:`src/mcp/tools/pathfinder.test.ts`)。

**怎么抓**:没有通用闸。可操作的替代是一条**提问纪律**:
> 写完一个机制,先回答「**它在生产的哪一次调用上会被执行**」。答不出具体路径 = 它还没上线。

### S-4 · 源表改了,但落盘的配置没重生成

**形状**:代码里的默认值改了,而运行时读的是一份旧的派生产物。

**为什么没红灯**:两边都自洽,只是不是同一份。

**本仓实例**
- worker 推理档 2026-07-31 从 `low` 改成 `high`,`.omd/config.json` 里一直是 `low` ——
  **生产跑了整整一天的 low**(2026-08-01 才发现)。

**怎么抓**:凡是"代码里的表 → 落盘成配置 → 运行时读配置"的链,
要么让运行时**直接读源表**,要么在启动时比对并告警。本仓选前者:
座位登记表 `src/model/seats.ts` 是真源,`role-models` / `auto-assign` / `empty-knobs` 全部**派生**。

### S-5 · 观测/判据锚在过期的量上

**形状**:一个判据读的数在它被读的那一刻已经不描述当前状态了。

**为什么没红灯**:数是真的,只是过期了;逻辑看起来完全正确。

**本仓实例**
- **压了等于没压**(2026-08-01):`estimateContextTokens` 优先拿最后一条 assistant **自报的 usage** 当基数
  —— 那是最准的,但压缩删的是它**前面**的消息,那条 assistant 自报的数仍是压缩前的。
  于是"压完再问还超不超"永远答"超",压缩照跑照付钱然后照样停(`before 3112 → after 3112`)。
- 一次 goal 产生**两条 trace**(contract 段故意把 runId 改写成 `<runId>-contract`),
  按 runId 查不到 trace 差点被判定成"修复失败"。

**怎么抓**:凡是"缓存/复用一个昂贵的量"的地方,写下**它什么时候失效**,
并让失效的那一刻有代码表达(本仓用置位-消费的一次性标志,而不是长期开关)。

### S-6 · 判据把 A 读成了 B

**形状**:判据本身能跑、也会触发,但它测量的东西**不是**它名字说的那个东西。

**为什么没红灯**:它照常给出裁决,只是裁决是错的。

**本仓实例**
- **「在想」被读成「没反应」**(2026-08-01):停摆闸数的是 `text_delta`,
  而模型推理时发的是 `thinking_delta` —— 对它完全隐形。
  effort 提到 max 之后,一个正常思考 50 秒的叶子会被当成挂死杀掉。
- `filesTouched` 只收顶层 `args.path`,而 `hashline_edit` 的路径嵌在 patch 头里 →
  真交付的文件节点被产物闸全判 failed(恒空 = "谎报完工")。
- fan-in 前缀那条用例拿「节点甲」「节点乙」当数据,**两者共同的「节点」二字**把分叉点推后了 ——
  测试数据自带公共前缀,量到的是假的。

**怎么抓**:给判据写一条**反向用例**——"什么情况下它**不该**触发",
并确认那条用例真的不触发。只测"该触发时触发"的网,抓不到 A/B 错位。

### S-7 · 同一条规则散在多处,漏掉第三处

**形状**:同一个不变量在 N 个地方各实现一遍,修的时候只修了 N−1 处。

**为什么没红灯**:改过的那几处都对。

**本仓实例**
- 「sessionId 没串下去」一个 session 里出现**三次**:`runDagInternal` 自造 UUID ·
  `run-goal:193` 又解析一遍 · judge 调用不带 meta。
- 「三个调用点共用」的注释写着共用,实际**三缺一** —— 空转 BLOCKED 出口根本不写 journal。
- 同一个叶子在两条路上**两个寿命**:MCP 传 1h,TUI/sec-audit/review 不传 → 吃 240s 默认。
- **command 闸的环境事实只进了两份 prompt 里的一份**(2026-08-01):白名单/元字符/`expect_exit`
  写进了规划 prompt,**补丁重规划 prompt 一个字都没有** —— 而修复轮恰恰专门在改被判失败的验证节点。
  live 3/3 复现:它把 `expect_exit:1` 改写成 `grep …; rc=$?; test "$rc" -eq 1`(规划 prompt
  明文禁止的 shell 取反),把另一个改写成 `$(cat …)`,双双撞注入闸 → **假红**。
  当初把白名单塞进规划 prompt 的判据(「conductor 只能猜,猜错就是假红」)原样适用于这条路,
  只是当时没数一共有几处。收法同上:`commandGateRules()` 一份,两份 prompt 都拼它。

**怎么抓**:发现一处时**先数一共有几处**,再决定是修还是收成一处。
本仓的收法:`seats.ts`(座位)· `model-caps.ts`(模型能力)· `pi-transport`(唯一传输)。
> 两条路各写一份,早晚一份先漂 —— 而漂掉的那份就是下一个事故。

### S-8 · 归因归错了层

**形状**:观察到的现象是真的,但把它归给了错误的原因,于是**修错了地方**,或者**记下了一条错的事实**。

**为什么没红灯**:结论听起来完全合理。

**本仓实例**
- 探针报「10 分钟内按 runId 查不到 trace」→ 差点判定修复失败;
  实际是 contract 段**故意**改写了 runId(探错了 id)。
- **把 temp=0 不确定当成"温度被忽略"的证据**(2026-08-01):
  MoE 服务端在 temp=0 下本来就不确定(batch 路由)。重做成 `top_p=0.01` 硬夹才有分辨力。
- **把「思考模式的性质」登记成「模型的固有属性」**(2026-08-01):
  写成无条件的 `honorsSampling: false`,顺手抹掉了"关掉思考就能调温"这个真实存在的选择。

**怎么抓**:下结论前问一句 —— **这个观察还能被什么别的原因解释?**
把那个替代解释**排除掉**的实验设计出来,再下结论。
拒因说的是哪一层,别替它归因。

### S-9 · 前提在别的宿主上不成立 —— 同一段代码,寿命变了

**形状**:一个对象的正确性依赖它**活多久**,而活多久由**谁构造它**决定。
换一个宿主(短命 CLI → 长驻 daemon),前提悄悄翻面,**代码一个字都没改**。

**和已有几条哪里不一样**:S-3 是机制**没跑到**某条路上;这一条是机制**跑了**,
跑在一条它的前提不成立的路上。S-7 是同一条规则写了两份;这一条只有一份实现、一份注释,
注释里那句话在 A 路上是真的、在 B 路上是假的 —— **没有第二份可对照,所以没有"漂"可查**。

**为什么没红灯**:单测里 runner 现建现用,前提永远成立,测试**永远绿**;
生产上它退化成"返回上一次的结果",而上一次的结果**看起来完全正常**。

**本仓实例**(2026-08-01,live 抓到)—— command leaf 的确定性 memo 缓存。
它的安全论证有两环,**两环都被实测证伪**:

- ①「新调用 = 新 runner = 新缓存」是个**没人钉住的前提**:TUI/eval 每次现建 → 成立;
  MCP 是长驻进程,`assemble` 装配期建**一次** → 缓存跨了这台 daemon 上的**所有** run。
  实测:两个 runId 之间改掉盘上文件,第二跑仍返回旧值;同图对照组(命令串多一个空格 →
  缓存键不同)读到新值,排掉了"下游复述时幻觉"。
- ②「单 run 内输入文件不变 → 无 staleness」**在这台引擎上天然为假** —— 它的本职就是让
  agent 节点改文件。实测:同一张图里 `cat f` → agent 写 f → `cat f`(同一命令串)
  读回的是**写之前**的内容。第一版修复(按图清缓存)只堵了 ①,**② 原样还在**。

**危害方向是最坏的那个**:只缓存 `exitCode===0` ⇒ 红→绿看得见,**绿→红看不见** ——
一条 `bun test` 闸在这台 daemon 上过一次,之后代码改坏了也照绿。
它还顺手废掉了引擎那条设计(「command 节点刻意不落绿 checkpoint,resume 重跑一遍比跳过一个闸安全」):
重跑发生了,结果来自缓存,**闸还是被跳过了,只是降到没人看的一层**。

**结局:删掉,不留旋钮。** 先修后删,是因为**收益侧的读数是补做的** ——
留痕库全量 12 次真实 run / 25 个 command 节点,同一 run 内**重复命令串 = 0**(唯一一次重复
是升级轮为了测缓存自己造的,而它给出的正是错的答案)。它连设计时说的主场景都覆盖不了:
「兄弟节点跑同一条命令」是同层并发,缓存只在命令返回后写入,两个都 miss。
零命中 × 两条错误绿灯 ⇒ 这不是"修好边界"的事,是**它压根不该在**。

**怎么抓**:三条。
> ① 写"per-X 缓存/状态"时,把 **X 的边界交给知道边界的那一层**,别让它由构造位置隐式决定。
> ② 一个**只快不对**的机制,先量它**到底命中过几次**再谈修 —— 收益侧没有读数时,
>   人会本能地去修边界(我第一版就是),而正确的问题是"删掉它会损失什么"。
> ③ 缓存/复用类机制的测试必须**跨两次调用、且中间让世界变一次**:
>   单次调用的测试对这一族天生瞎,而"世界不会变"恰恰是它们最爱写的那个假设。

### S-10 · 判官是真的,喂给它的证据被沿途削掉了

**形状**:一道判定闸**确实在跑**、判据也写得对,而它看到的输入**被上游悄悄削掉了一块**。
于是它照着自己的判据给出裁决 —— 裁决是错的,但**推理是对的**,判词读起来完全合理。

**和已有几条哪里不一样**:S-1/S-2/S-3 说的是机制没跑或没接上;这一条**全接上了**。
S-6 是判据把 A 读成了 B(测错了东西);这一条判据没读错,是**东西根本没送到**。
要害在于:它的判词会把你引向"这个模型太严了 / 换个模型试试" —— 而真正该改的在上游三十行外。

**为什么没红灯**:每一段都自洽。命令跑了、退出码是 0、输出非空、节点 done、判词有理有据。

**本仓实例**(2026-08-01,一轮里撞到两次,都是被同一道闸的判词逼出来的)
- **`summarizeResults` 不给命令串与退出码**:终审看见一个裸的 `93`,不知道它是哪条命令跑出来的。
  它的判词逐字写着「未展示所执行的具体命令与退出码」—— 而这两样引擎手里都有
  (`plan.nodes[id].command` · `LeafResult.exitCode`)。补上之后同一条样本 0/3 → **3/3 判过**。
- **command leaf 的 `(stdout || stderr)` 二选一**:`bun test` 把版本横幅写 stdout、
  把 **`N pass / N fail` 汇总写 stderr** → 一个验证节点的全文输出只有 `bun test v1.3.14`。
  通过/失败数**从没进过** DAG、下游、终审或留痕库。而 conductor prompt 恰恰教它

### S-12 · fail-open 吞掉的不是异常,是**证据**

**形状**:一处 `try { … } catch { /* 不该把一次真跑炸掉 */ }`。**这个判断通常是对的** ——
持久化失败不该杀死一次正在跑的活。但如果 catch 里**一个字都不留**,它同时销毁了
「这次降级过」这个事实,于是「成功了」与「失败了但我们决定继续」在事后**完全不可区分**。

它与 S-1 的区别:S-1 是机制没有消费者;这一条是**机制正确执行了它的降级路径,而降级本身不可观测**。

**为什么没红灯**:按设计它就不抛,所以任何"有没有异常"的检查都是绿的;
更麻烦的是**内存视图仍然自洽** —— 进程内每一次读都拿到"正确"的新状态,
只有另一个进程(或重启后的自己)才看得见分歧,而那时现场早没了。

**放大它的一条实现顺序**:

```ts
rec.status = to;        // ← 内存先改
this.persist(runId);    // ← 落盘在后, 且 catch 是空的
```

落盘是**持久真相**,内存只是缓存。先改缓存再写真相,一旦写失败,两边必然分歧,
而分歧的那一侧恰好是没人看的那一侧。

**本仓实例**(2026-08-02,一次 30 分钟的 live `dag_goal`)
- 症状:`goal-worker` 打印「终态 done」并 exit 0,而 `.omd/runs.db` 里那个 run
  **至今停在 `running`**,`updated_at` 停在起跑那一刻;同一次跑的 `dag-runs.db` **零行**。
- 两层 catch(`RunRegistry.persist` + `run-store.put`)**都一声不吭**,
  于是唯一能拿到的线索就是"两个库对不上",排查时无从下手。
- 排查代价:七个假设逐个证伪(改动本身 · SQL/schema · `process.exit` 丢 WAL ·
  `succeed` 不持久化 · 写错库 · worker 形状 · 引擎吞钩子异常),**触发原因至今未定位**
  —— 因为该留证据的那一刻什么都没留。
- ⚠ 原注释写着「记不下来最多是重启后少认得一个 runId」。**这句低估了代价**:
  对 detached run(无人值守跑完就走),盘上那条**就是唯一的出口**,
  丢了等于这次跑的结论没有任何人看得到。

**怎么抓**:没有通用闸(它是运行时条件,不是结构)。两条可执行的纪律:

> ① **每一个 fail-open 的吞点必须留一行**(runId / 状态 / 错误消息)。
>   吞掉异常可以,吞掉证据不行。「过了一道」与「过了两道」不是一回事,
>   同理「写成功了」与「写失败了但我们继续」也不是。
> ② **缓存与持久真相的更新顺序**:要么先落盘再改内存,要么在失败时把分歧**显式记下来**。
>   先改内存后落盘 + 空 catch = 保证分歧且保证无声。

**这条纪律抓不到的**:它只让下一次可诊断,**不解释这一次**。
本仓那次的触发原因仍是 `Unobserved`,不是 `Missing` —— 别把"装了灯"当成"修好了"。

#### 第二次复现(2026-08-03,`t9b-6008b42`)—— 灯喊了,而且这次量到了两个数

灯按设计工作:响亮喊出现场、三次重试直写、如实退非零。**新证据三条**:

**① 内存/磁盘压力这条候选机理**(此前从没量过的两个数之一)**排除。** 失败当时
可用内存 **32.6 GB**(空闲 28.4 GB)、磁盘空闲 **651 GB / 用量 32%**。不是资源耗尽。

**② 并发连接这条**(另一个从没量过的数)**强相关,而且是一次干净的自然实验。**
同一天同一台机器上跑了四次 live:

| run | `runs.db` 上有没有第二个进程 | 写穿核验 |
|---|---|---|
| `g6live-…` · `t7b-…` · `t8b-…` | **没有**(omd MCP 整个 session 断开着) | `consistent` ×3 |
| **`t9b-…`** | **有** —— `cli.ts mcp` (pid 1022845, 12:56:45 起, `/proc/<pid>/fd` 确认持有 `runs.db`) | **`unrecoverable`** |

混淆变量整天只出现过一次,失败也只出现在那一次。⚠ 这是**相关不是证明**(n=1,且非受控),
但它与 `REPAIR_ATTEMPTS` 注释里那个"头号嫌疑"(同文件并发连接的 WAL/shm 生命周期竞争)指同一处。

> **⚠ 同日的一条负结果,把 ② 的强度往回收了一格。** 事后清那个孤儿时做了一次准受控试验:
> **让 MCP server 继续持有 `runs.db`**,从第二个进程调 `verifyTerminalPersisted` 直写 ——
> **一次就成(`repaired`)**。所以「存在第二条跨进程连接」**本身不足以**触发这一族失效。
> 机理里一定还有**时机**那一维(最可能是 worker 自己 `registry.close()` 的 WAL checkpoint
> 与另一进程的操作在同一瞬间交叠,而不是"连接同时存在"这个静态条件)。
> 别把 ② 读成「并发连接 = 会炸」—— 它只说明失败那次恰好有并发连接,而并发连接常态下无害。

**③ 丢的是账本,不是产物。** 事后查:`omd_runs` 里**那一行在**(`status='running'`,
`owner_pid` 是已死的 worker),表在,库读得动;而那次跑的**代码产物完好落盘、oracle 全绿**。
所以这一族的真实代价是「run 变孤儿」,不是「活白干」—— 比原条目暗示的轻,但对
detached run 仍然致命(盘上那条是唯一出口)。

#### ⚠ 本次最锋利的一条:**S-12 的灯里面自己有一个 S-12**

`verifyTerminalPersisted` 报的是「盘上=**无此行/库不可读**」—— 一句带斜杠的话,
因为它的 `readDiskStatus` 把两种结局压成同一个 `null`,而那个 `catch` 是**空的**:
异常连同它的消息一起丢掉。

**这次那条被扔掉的异常就是全部诊断**:事后确认行在、库读得动,所以当时的 `null`
只可能来自**读失败**。而「行不在」指向写路径、「库读不了」指向并发/文件系统——
**诊断方向相反**。在最需要分辨的那一刻,灯分辨不了,原因是它自己犯了它要抓的那条。

已修(`src/mcp/terminal-verify.ts`):`readDiskStatus` 返回三态
(`row` / `no-row` / `unreadable` + 错误原文),报错行分别说,并直接印出方向指引。

顺带修掉一条**由此才看得见的数据丢失路径**:原修复逻辑按上一次读的结果二选一——
读到行 → `UPDATE`,读不到 → **`INSERT OR REPLACE`**。而读不到 ≠ 行不在,
于是在"行在但当时读不了"这一格(正是本次现场),修复会把真行的
`goal`/`meta`/`created_at` **覆盖成空** —— 为了修一个状态字段毁掉这次跑的全部身份。
改成一条 upsert,两种情形都对,且不依赖"上一次读是准的"这个前提。
闸:`terminal-verify.test.ts` 的「修复不碰 goal/meta/created_at」(证伪过,换回
`INSERT OR REPLACE` 即转红)。

**仍然 `Unobserved` 的**:什么条件下读写会双双 I/O 失败,机理没定位。
上面那条负结果已经排掉了最简单的那个说法(「有第二条连接就会炸」是错的),
剩下的候选要窄得多也难测得多:**收尾瞬间的时机交叠**。想坐实得造出那个窗口 ——
在 worker `registry.close()` 的 checkpoint 那一刻让另一进程开合同一个库,而不只是让它开着。
**别把"排掉一个说法"当成"定位了机理"。**

### S-16 · 产物闸把「闸看不见」说成「它没做」

### S-21 · 读数板上有一段**只活在渲染层** —— 于是它自己数了一遍,没有任何闸碰得到它

**形状**:一份读数板里绝大多数段都从**类型契约**取数(有契约就有测试,有测试就有反向自检)。而有那么一两段是当初"顺手在打印的地方算一下"写出来的:它拿原始行自己数一遍,数完直接 `console.log`。**它没有类型、没有断言、没有反向自检**,于是它可以带着一个算错的口径活很久 —— 而且因为它印出来的数看着完全正常,谁都不会去查。

**和已有几条哪里不一样**:S-19 是分母没被写过、S-20 是判词把几件事并成一个括号 —— 那两条错在**内容**上,而它们所在的段**是有契约的**,补完就能立刻立闸钉住。这一条错在**位置**上:同样的内容错误发生在一个测试够不着的地方,于是它比前两条活得更久。它也是前两条的**放大器** —— 想给它立闸,得先把它搬进契约。

**为什么没红灯**:`console.log` 的字符串不进类型、不进断言。全仓 2700 条测试没有一条 import 得到它。变异测试也测不到:破坏它,一条都不会红。

**本仓实例**(2026-08-06,顺着 S-20 问「这一族还有多少实例」查下去撞到的两个)
1. **⑥ 熔断键那段把结论读反了**。它只分两格:`nearMiss`(同输出不同命令)与 `exactRepeat`(同输出同命令)。可 `cmds.size === 1` 对一个**只出现过一次**的指纹同样成立 —— 而熔断按构造要「≥2 次」,单次失败**两种键都抓不到**。实测:指纹 25 种 · singleton **22** · 真有机会 **3** · near-miss 3 · 真重复 **0**。旧读法让人算出「现行键覆盖 22/25 = 88% → 够用」,而在真机会分母上现行键的覆盖是 **0/3**。**方向相反。**
   > 改完渲染出来**当场又照出两层**:① 3 组 near-miss 里 2 组是**跨 run 凑出来的**,而 §8.4 熔断是同一次 run 的环内累计,跨 run 的两次失败根本碰不到一起;② 有一个桶是 `sha1('')` —— 所有 `grep -q` 式**空输出**的失败全指纹成同一条(实测 2 条互不相干的命令)。把它算进 near-miss 等于说"改宽键能多抓到它们",而那恰恰是设计注里早就警告过的**误熔断**。**它是反例不是机会。**去掉两层污染后真机会只剩 1 组。
2. **⑨ 与 ⑫ 对同一件事印两个数**,同一页、同一个词 `outcome`,差 **2.8 倍**:⑨ 数**全量留痕记录**(56 条 / 53 个 runId),⑫ 按 **runId 归并**且只取最早 `limit` 个 run(20)。而 ⑫ 上面那句「run 统计(分布/判据/entry)= 窗口」读起来像是替整份报告作声明 —— ⑨ 同样是 run 级分布、同样带判据,却既不归并也不截窗。量过之后:归并只差 3 条,**窗口才是那 2.8 倍**。

**怎么抓**:`src/harness/omd-readout.test.ts`(⑥ 六条,含「三格互斥且穷尽」)。
> 加一段读数时先问:**它的数进契约了吗?** 没进 = 你正在写一段没人能闸的读数。
> 证伪:复原旧算法(`exactRepeat` 不要求 `hits >= 2`)→ 两条当场红。

### S-22 · 事后重建出来的量,**算得没错,但它量的不是你以为的那件事**

**形状**:拿留在盘上的痕迹去重建一个历史读数(时间窗、次数、配对)。计算本身没问题,分母也写了,门槛也钉了 —— 而**从数据到现实的那一步映射**建立在一条**没被检查的假设**上。于是你得到一个真实存在、可复现、看着完全正常的数,它只是**不回答你问的那个问题**。它比 S-19(没有分母)更难发现:那一类你会觉得心虚,这一类你会觉得踏实。

**和已有几条哪里不一样**:S-19 是分母没被写过、S-20 是判词把几件事并成一个括号、S-21 是这一段没有契约管得着 —— 那三条错在**仪器**上。这一条的仪器完全正常:它错在**「这批数据的每一条代表什么」**这个**读法**上,而读法通常不写在任何地方,它活在建仪器那个人的脑子里。

**为什么没红灯**:重建出来的数**处处自洽** —— 有分子有分母,门槛在数据到达之前就钉死了,反向自检也会红。唯一错的那一步(数据 → 现实的映射)**不是任何一条断言的对象**。

**本仓实例**(2026-08-06,⑧.7 回溯写竞争;实例的全部价值在于它是**照自己写的判词去核自己建的仪器**才发现的)
- 拿 `.omd/continuity/<runId>/<nodeId>.json` 的 `createdAt - durationMs` 重建执行窗口、比 `outputPaths` 交集,算出「历史上并发写竞争 30 机会 / 1 撞车」,并据此写下**「并发写竞争在生产上确实发生,不是理论风险」**。
- 没被检查的那条假设:**「一个 nodeId 一份 checkpoint = 一次执行」**。而 checkpoint 按 nodeId **覆写**,多轮内环里同一个节点会跑好几次 —— 于是两份 checkpoint 可能来自**不同的轮**,而「两个节点在不同轮里各跑一次」**根本不是并发**。
- 拆开之后结论反过来:**单轮跑(无歧义)0 撞车 / 21 机会**,而那唯一一条**整条落在多轮跑那一面**(1/9)。
- 顺带还有第二层:归档文件 `<nodeId>.__r<K>.json` 让**同一个 nodeId 在盘上有好几份**(实测 9 个目录 / 43 个节点),配对函数会把「同一节点的第 1 轮与第 2 轮」配成一对 → 两轮写的通常正是同一批文件 → **保证撞车**。
  > ⚠ 诚实标注:这第二层**在那批数据上没有兑现**(不同轮的窗口在墙钟上本来就不重叠)。守卫是构造性防护,不是对已观测错数的修正 —— 我第一反应写的是"历史数字被污染了",**那句说早了**。

**怎么抓**:`src/harness/omd-readout.test.ts`(⑧.7 十条,含「不同轮不算一对」「同一节点不能和自己撞车」「按 runId 分组是硬约束」)· `NodeCheckpoint.round`(2026-08-06 起记轮次,新跑自动进可信面)。
> 重建一个历史读数之前,先把**「这批数据的每一条代表什么」**写出来,再问**哪条假设会让它不成立**。
> **新仪器的第一条 finding 必须人读** —— 仪器新建时最容易发生的不是"数错了",是"数对了但量的不是那件事"。
>
> ⚠ **这一族(S-19/S-20/S-21/S-22)有一条共同的找法,值得单独记下来:**
> 2026-08-06 这一程一共抓到**四次**(⑥ 的结论是反的 · ⑧.7 的单位错了 · ⑧.6 的判词只念了一半 ·
> ⑨/⑫ 两个 outcome 不可比),**四次全部来自"把真实输出印出来盯着看"** ——
> **没有一次来自通读代码**。原因是这一族的错**在代码上是自洽的**:分子分母都在、
> 门槛先钉了、反向自检也会红,唯一错的那一步(数据↔现实的映射、判词↔下一步的映射)

> → **改完读数板要跑一遍并逐行读**,尤其是样本行(`da39a3ee5e6b` 一眼认出是 `sha1('')`

### S-23 · 派生量的谓词**永假**,而它的夹具让它看起来在工作

**形状**:一个"推"出来的量(不是记下来的,是从别的字段推的)。推的那条谓词建立在**一个关于数据形状的假设**上,而那个假设是错的 —— 于是谓词**在真数据上永远为假**,那个量恒为 0。而**它的夹具是照着同一个假设造的**,所以测试是绿的、还证明"推断工作正常"。

**和已有几条哪里不一样**:S-15 是判据**结构上够不着**那条路(它压根没跑);这一条**每条记录都跑了**,只是那个谓词永远不成立。S-22 是重建出来的量**单位错了**(数是真的,量的是别的事);这一条**连数都是假的**(恒零)。S-19 是分母没被写过;这一条**分子恒零而分母正常**,所以它印出的是一个漂亮的 `0.0%` 而不是"算不出"。

**为什么没红灯**:`0.0%` 是一个**合法的读数**,它不像 `null` 那样刺眼。而唯一能戳破它的是**同一件事的另一个数**——如果没有第二个口径,这个假零可以活到永远。

**本仓实例**(2026-08-06,盯着 ⑫ 段读时,靠**同一页上两个数打架**才发现的)
- 读数板同一页上:⑩ 段「复用率 **21.9%**」(按 run 自报的 `reused` 计数)· ⑫ 段「复用率 **0.0%**」(按节点面推)。**0% 与 21.9% 会导向完全相反的结论**(「复用根本没在工作」vs「复用正常」)。
- 谓词:「节点在 plan 里、**不在执行结果里**、且更早跑过 → 那是复用」。**而复用节点就在结果里** —— 引擎是 `results[cid] = { ...上轮结果, skipped: true }`。于是谓词恒假。实测:**32 条记录声明过复用(共 ~123 节点),推断出 0 个**。
- **夹具是照着那个假前提造的**:`done: ['y'], reused: ['x']` —— `x` 不进 `results`。于是推断在夹具上工作、在生产上恒零。**实装与测试一起错,并且互相背书** —— 本仓 CLAUDE.md 早写着这一条(「测试与实装由同一次改动一起产出时会一起错」),这是第一次亲手撞到。
- 修:`DagRunNode.reused?: true` 从 `result.reusedNodes` **记下来**,不再推;老行(声明了复用而节点面没标)单独数 `unknownRuns`,**不进分母** —— 它们是**算不出**,不是"没复用"。

**怎么抓**:`src/harness/omd-readout.test.ts`(复用率口径 2 条,含「老行算不出不许当 0」)· 夹具已改成像真引擎(复用节点进 `results` 并带 `skipped`)。
> 见到一个**推**出来的量时,先问:**它的谓词在真数据上可能为真吗?** 拿一条真记录手算一遍,别信夹具。
> 而**发现它的唯一实用办法是给同一件事留第二个口径** —— 两个数打架时才有人会去查。
> ⚠ 推论:**别急着把"重复的两个指标"合并成一个** —— 那正是这次戳破假零的那一根针。
>
> ⚠ **顺着这条推论把整块板对了一遍账,结果本身是一条读数**:同一块读数板上找到
> **五对**"同名不同义"的数,而**其中只有一对是错的**(复用率那个假零),另外四对都是
> **两个都对、答的不是同一个问题**:
>   ⑨/⑫ 的 `outcome`(全量记录 vs runId 归并+窗口,差 2.8 倍)·
>   ⑧/⑧.1 的"转了几轮"(走到比较点 vs 转到第二圈)·
>   ⑩/⑫ 的判据轴(全量 vs 窗口)· ⑦/⑫ 的"没过的节点"(实例计数 vs 去重且判"有没有成功过")。
> **四对合法、一对是缺陷 —— 而在标口径之前,五对长得一模一样。**
> → 所以第一步永远是**标口径**,不是"统一算法":统一算法会把四对合法的差异抹平,
>   同时把那一对缺陷藏得更深。

### P-1 · **写的人自己的偏差** —— 倾向于把事情说得比实际更简单、更乐观

> ⚠ 这一条与上面 S-* 那些**不同类**:S-* 是**代码/记录**的静默失效,这一条是**写这些东西的人**
> 的失效。放在同一份图鉴里,是因为它的后果一模一样 —— **报得对、读起来正常、没有任何一层报错**,
> 而下一个人照着做就走错路。编号用 `P-`(process)与 S-* 分开。

**形状**:每当要下一个判断(「X 就够了」「X 是最常见的」「改 X 就行」「这说明 Y」),
在**还没去盘上找一条能证伪它的记录**之前就把它写出去了。它读起来完全正常 ——
有理有据、有上下文、甚至有数 —— 只是那个数**没被逼问过**。

**为什么没红灯**:没有任何闸检查"这句判断是否被证伪过"。测试测的是代码,不是结论。
而这类句子**天然自洽**:它们通常是从一个真读数出发的,只是**多走了一步没验的推理**。

**本仓实例**(2026-08-06 一程之内,**推翻自己 9 次**,方向完全一致)

| 我先写的 | 往下查一层之后 | commit |
|---|---|---|
| ⑥「现行熔断键覆盖 88% → 够用」 | 真机会分母上 **0/3**,**方向相反** | `57575ed` |
| 「收窄 `SHELL_WRITE_BLIND_SPOTS` 最常见」 | 113 条命令认得出写目标 **0** 条,**零收益** | `1c9a7ad` |
| ⑧.1「②③④ 要跑一次新的才有数」 | ④ **回溯就有答案**(journal 里一直有) | `bf05865` |
| ⑧.7「并发写竞争确实发生」 | 唯一那条**排除不掉跨轮伪影** | `00be821` |
| 「历史数字被污染了」 | 加守卫前后**逐位相同**,没兑现 | `2b163db` |
| ⑧.6 判词「够不着」 | 压着两件事,**只念了一件** | `29c0901` |
| 判据轴「judge 太紧 → **白转了几轮**」 | 内环判据绿就收敛,**一轮都没白转** | `f939cfb` |

| 「改一句 prompt 就行」 | 那里**根本没有 prompt**(纯正则) | `285c1b6` |

**九次全部是"往下多查一层"查到的 —— 没有一次是坐着想明白的。**

还有一次**元实例**:我在对话里说「这一条我记在交接里了」,而**当时并没有记**。
**说了做过而没做,与本图鉴治的那些静默失效同形。**

**怎么抓**:没有闸,只有一条**动手前的提问纪律** ——
> **任何一句形如「X 就够了 / X 最常见 / 改 X 就行 / 这说明 Y」的话,
> 在写进判词、交接、或回给 owner 之前:去盘上找一条能证伪它的记录。找不到,再写。**
>
> 具体动作(这九次全靠它):**再往下查一层** ——
> · 说"这条路最常见"→ **数一遍**它在盘上占多少;
> · 说"要等新数据"→ **先问哪一格可回溯**;
> · 说"改一句 prompt 就行"→ **打开那个文件看有没有 prompt**;
> · 说"某某机制该做宽"→ **先查是什么在喂它**;
> · 说"我记下来了"→ **grep 一遍**。
>
> ⚠ **偏差方向是单向的**:九次全部是"我说得比实际更简单/更乐观",没有一次相反。
> 所以自查时**不必两边都查** —— 只查"我是不是说轻了"。
>
> ⚠ **它也发生在"做总结"时,而且那时更难察觉**(2026-08-06 第 12 次实例):
> 我把三件互不相干的事收成一句「**所有隔离能力都挂在同一个从没被打开的开关上**」——
> 查完发现只有一件挂在那个开关上,另两件一件是**没有可达调用者**、一件**根本不是开关**
> (是个无条件跑的测量)。**三个不同的因,对应三个不同的修法;合并会产出一个错的修法。**
> → **把散的东西收成一个故事时读起来像洞察,而那正是它最危险的时候。**
> **总结句同样要过那一关:那句"其实都是同一件事"——去逐条验一遍。**

### P-2 · **把"我没查过"说成"事实如此"** —— 而且它专挑**便宜到不该猜**的东西

> P-1 是"从一个真读数多走了一步没验的推理"。**P-2 更低级也更贵:压根没有那个读数。**

**形状**:一个**几秒钟就能验**的事实,我用**间接信号倒推**出一个答案,然后把它当成事实

>   `git log` / 一次 API 调用 / `grep -c` 这个量级的,**没有任何理由用推的**。
>
> **③ 措辞闸**:凡是「一整年 / 一直 / 从来 / 全部 / 唯一 / 最」这类**量化副词**,
>   写之前先问它背后那个数在哪。查不出数就**把副词删掉**,别用修辞补。

## 怎么加一条

1. 确认它满足上面三条判据(尤其第 3 条:**两边都不报错**)。
2. 归到已有形态,或开一条新的 —— 新形态要说清**它和已有几条哪里不一样**。
3. 写实例时带上**当时的症状**(它伪装成了什么),那比缺陷本身更有复用价值。
4. **给出抓法。** 能自动化就落成测试并登记进上表;不能自动化就写成一条可执行的提问纪律。
5. 如果这一条是**自己犯的**,照写不误 —— S-8 的三条里有两条是。
