# pack eval 协议 —— 证明"你的 pack 真有用"的标准流程

> 给 pack 作者的照抄模板。参考实现:`templates/packs/tdd-bugfix/eval/`(两轮真跑,32 个 run,
> 每一条规则下面都标了它是被哪次踩坑逼出来的 —— 这些坑你不会想再踩一遍)。
>
> **核心立场**:能力主张 = 读数表。README 里的形容词不算数,卡被派上了不算数,
> 模型说做完了不算数。这套协议的全部目的是让**作者自己的臆想**也过不了关。

## 0. 目录布局(照抄)

```
<your-pack>/eval/
  PLAN.md                     # 四要素预声明 + 读数表 (跑前写死判据, 跑后填表)
  tasks/<task-name>/          # fixture: 种了缺陷的世界 + BUG_REPORT.md (给执行体看)
  oracle/<task>.oracle.ts     # 隐藏判据 (⚠ 不叫 .test.ts, 见 §3)
  readings/<task>-<arm>.jsonl # 逐跑读数 (机器写, 别手改)
```

## 1. 四要素(动手前写全,缺一不算实验)

| 要素 | 具体到 pack eval | 反例(踩过的) |
|---|---|---|
| **单一变量** | 世界里装 / 不装 pack。座位、任务文本、脚本信号、轮上限全部两臂相同 | 顺手换个 leaf 座位再比 —— 分不清是卡的功劳还是模型的 |
| **预声明信号** | 跑之前写死 S1..Sn 与各自"成立方向";事后不改 | 跑完看着数据挑一个好看的指标当判据 |
| **同条件基线** | 对照臂在**同一批次、同一天、同一座位**现跑现量;两臂 ABBA 交错消序 | 拿上周的跑当基线;两臂分两天跑 |
| **两侧都记** | 没差也是结论("卡在此任务无增益"值钱);更差更值钱 | 只把好看的那轮写进 README |

## 2. 信号设计:只认行为差,不认过程自述

**判据必须落在 oracle 可见的结果上。** "conductor 派了卡"、"leaf 说它跑了测试"都不是信号 ——
prompt 里的东西无法证明被读(本仓实测:讲道理拦不住)。参考实现的四个信号:

| 信号 | 怎么机械算 | 为什么这么设计 |
|---|---|---|
| S1 任务成功 | 隐藏 oracle 全绿的比率 | 唯一的能力面判据 |
| S2 纪律率 | 引擎记录里 `expect_exit:1` 节点真跑出退出码 1 的比率 | 卡承诺的"先复现再修"由退出码证明 |
| S3 违规率 | `filesTouched` 命中受保护文件的比率 | 作弊(改测试让它绿)必须能被抓 |
| S4 成本 | run 账本 token + 墙钟 | **不设方向**:纪律可以更贵,贵多少要知道 |

## 3. 隐藏 oracle 的三条硬规则

1. **执行体全程不可见** —— 跑完才拷进世界。可见的 oracle 会被当成"要过的测试"照抄,
   于是你测的是抄写能力不是修复能力。
2. **不以 `.test.ts` 命名**(叫 `*.oracle.ts`)—— 否则仓库全量 `bun test` 会自动发现它,
   而它对种了缺陷的 fixture 必然红。**oracle 的红属于 eval 时刻,不属于 CI**。
3. **判据必须能从任务文本导出** —— BUG_REPORT 里没写的规格,oracle 不许考。
   否则两臂都在猜谜,读数量的是运气。

**oracle 判别力自证**(必做,参考 `src/harness/pack/reference-pack.test.ts`):
种缺陷世界上 fixture 自测**绿**(缺陷没被既有测试盖住 = eval 前提成立)、
隐藏 oracle **红**(oracle 判得出缺陷)。两条缺一,整个 eval 白设。

## 4. 任务难度校准(v1 最贵的一课)

**先证任务有区分度,再谈 pack 有没有用。** 参考实现 v1 用单函数 bug,裸引擎活跑 100% 修好 ——
编排在此没有增益空间,读数量不出任何东西,烧掉 16 个 run 才明白。

跑之前预声明**任务有效性判据**:
- 对照臂成功率 **≤60%** → 任务有区分度,读数可当能力结论;
- **≥80%** → 任务太易,本轮只算任务校准失败,**不得当能力结论用**;
- 中间是灰带 → 判"边缘成立",结论降级为方向性。
  (⚠ 参考实现 v2 的 62.5% 恰落灰带 —— 阈值留洞是判据设计缺陷,你写的时候把灰带口径也定死。)

## 5. 噪声治理:先排除通道故障,再谈能力

参考实现 v1 有 **9/16 个 run 是"死叶"**:执行体几乎零输入、产物一字未动、1-3 分钟就结束 ——
不是能力失败,是执行通道当时不可用。这类跑混进分母会把信号整个淹掉(它一度让我得出
"成本 40× 且零增益"的错误结论,直到逐条读失败原文才翻案)。

**机械判 + 剔除**(照抄 `scripts/eval-tdd-pack.ts` 的 `isChannelDead`):
- 判据:全部叶子零文件写 且 总输入 token < 阈值 → 判通道死;
- 处置:自动重试一次;仍死则标 `channelDead`,**不进能力分母**(但在读数表里如实列出);
- 预防:连跑之间留间隔(参考实现 15-20s),ABBA 交错。

## 6. 出口纪律

- **分层写,不熔账**:死跑/活跑、任务 A/任务 B 分开列。合并数会把"通道故障"读成"能力差"
  (v1 的原始错误就是中位数落在死跑堆里)。
- **n 要够**:n=2 是管道验证不是结论(参考实现 pilot 2/2 全绿,n=8 打回未证)。
  能力结论 n≥8/臂起步;要判统计显著大约需要 n≥20/臂。
- **算一下 p 值再说"有效"**:参考实现合并 8/11 vs 9/9 看着漂亮,Fisher p≈0.24 —— 未过线,
  所以最终结论写的是"方向性有效",不是"有效"。
- **读数表空着就明说未跑**;跑砸了照实写。空表期间不许在 README 写"显著提升"。

## 7. 最后一条(也是最难的一条)

这套协议第一个拦下的,是**写这套协议的人自己的 pack**:pilot 看着 2/2 完美,n=8 打回未证,
换难任务才拿到方向性证据,而且到最后也没过显著线。

如果你的 pack 跑出来"没有可测增益",那就是一条真结论 —— 写进表里,比一句没有读数的
"显著提升"值钱得多。
