# 静默失效图鉴 —— 「机制在、生产零生效」

> **这不是 session 记录,是一份长期台账。** 它收的是这个仓**反复撞见的同一族缺陷**:
> 机制写好了、配置项也在、测试全绿,而它在生产上一次都没生效过 —— 并且**没有任何红灯**。
>
> 为什么值得单独一份:这一族的每一个实例,当时都是"靠撞"发现的,不是靠计划。
> 写下形状之后,下一次可以靠**认**——甚至靠**闸**。
>
> 每加一条,请一并回答:**怎么抓**(最好是一条可自动化的判据)。
> 只描述现象而没有抓法的条目会退化成读物。

---

## 判据:什么算这一族

三条同时成立:

1. **声明面存在** —— 有配置项 / 有字段 / 有函数 / 契约里写着;
2. **消费面缺席或错位** —— 没人读它,或读的是另一个东西;
3. **两边都不报错** —— tsc 绿、测试绿、运行不抛,症状伪装成别的东西。

第 3 条是要害。会报错的缺陷不属于这一族 —— 它们一次就被发现了。

## 图鉴

### S-1 · 声明了但没有消费者

**形状**:schema / prompt / 座位表里出现一个字段,引擎里没人读它。

**为什么没红灯**:zod 容忍未知字段;prompt 是字符串;座位被 auto-assign 派了模型、被起跑自检查了凭证——**看起来全都在动**。

**本仓实例**
- `max_retry` / `on_failure` / `fallback` 三个 node 字段零消费者。
- `postcondition` 被两个 conductor prompt 反复明示,而引擎从不检查 —— 更坏的是它**把 conductor 从真的会跑的 command / judge 节点那条路上引开了**(写了个验证的样子)。
- `escalation` 座位纯装饰:auto-assign 给它派模型,引擎读的却是 `OMD_CONDUCTOR_ESCALATION_MODEL`。
- `gate.thinking` 写在座位登记表里,而 `llm-judge` 根本不传 `thinkingLevel`(2026-08-01)。
- `verifier.thinkingLevel` 硬编码 `'xhigh'`,座位里写什么都到不了调用上(同上)。

**怎么抓**:`src/harness/empty-knobs.test.ts`
- 「明示即承诺」:conductor prompt 里出现的每个 node 字段,必须登记 `file:line` 级消费点。
- 「座位即承诺」:`ALL_SEATS` 每个座位必须有解析点。

**这道闸抓不到的**:① 见 S-2 —— 它只问"有没有人解析",不问"解析出来的东西有没有被用在它该用的地方";
② 见 S-11 —— 也不问"解析它的那个文件本身有没有人调"(`dream` 座位就是栽在这里,由可达性闸补上)。

### S-2 · 坐标被人用 ≠ 它代表的机制在跑

**形状**:一个配置项**确实被读了**,但读它的是另一个用途;它本来该驱动的那道机制从没启动。

**为什么没红灯**:所有"有没有人读"的闸都会绿。

**本仓实例**(2026-08-01,最贵的一条)
- `verifier` 座位在 MCP 路径上**确实被解析** —— 被借去组 `stampPools.strong` 那个池。
  于是「座位自检 16/16 ✓」与「跨模型终审闸一次都没跑过」**同时成立**。
  `config.verifier` 只在 `tui.ts` 里被设过;`tools/dag-tools.ts` 里那句
  「MCP 路径无 verifier」的注释,就是当年照着这个事实改下游判据时留下的。
- `judgeModel` 从不被装配层给出 → 引擎落回 `?? config.conductorModel`,
  于是「判这一轮收敛没有」的那一发一直**骑在 conductor 座上**,改 judge 座位不生效。

**怎么抓**:`src/mcp/seat-wiring.test.ts`
判据取**引擎真收到的 config**,不是"装配层有没有那行代码"——后者是看着像验了。
> 加一道新的引擎能力时问自己:**它的开关在哪条路径上被真的传进去了?** 两条路径都传了吗?

### S-3 · 机制写好了,但默认关着 / 只挂在一条路上

**形状**:能力完整、注释详尽、甚至有测试,而生产从来没吃到。

**为什么没红灯**:它是"可选增强",不给就是不给。

**本仓实例**
- `warmThenFanout`(暖发共享前缀)早就写好,默认 `false`,**只有两个 eval oracle 开过**。
- `createDagRecorder` 只挂在 TUI 侧的 `/cg /audit /iterate` 上,MCP 这条从没接过 →
  生产路径上那个库恒空,「一次 goal 多少钱」与「兄弟节点吃到多少缓存」两个问题都没有数据源。
- auto-compaction:老 `createAgentSession` 自带,搬到低层循环时弄丢,只留"到线就停"(2026-08-01)。

**怎么抓**:没有通用闸。可操作的替代是一条**提问纪律**:
> 写完一个机制,先回答「**它在生产的哪一次调用上会被执行**」。答不出具体路径 = 它还没上线。

### S-4 · 源表改了,但落盘的配置没重生成

**形状**:代码里的默认值改了,而运行时读的是一份旧的派生产物。

**为什么没红灯**:两边都自洽,只是不是同一份。

**本仓实例**
- worker 推理档 2026-07-31 从 `low` 改成 `high`,`.omd/config.json` 里一直是 `low` ——
  **生产跑了整整一天的 low**(2026-08-01 才发现)。

**怎么抓**:凡是"代码里的表 → 落盘成配置 → 运行时读配置"的链,
要么让运行时**直接读源表**,要么在启动时比对并告警。本仓选前者:
座位登记表 `src/model/seats.ts` 是真源,`role-models` / `auto-assign` / `empty-knobs` 全部**派生**。

### S-5 · 观测/判据锚在过期的量上

**形状**:一个判据读的数在它被读的那一刻已经不描述当前状态了。

**为什么没红灯**:数是真的,只是过期了;逻辑看起来完全正确。

**本仓实例**
- **压了等于没压**(2026-08-01):`estimateContextTokens` 优先拿最后一条 assistant **自报的 usage** 当基数
  —— 那是最准的,但压缩删的是它**前面**的消息,那条 assistant 自报的数仍是压缩前的。
  于是"压完再问还超不超"永远答"超",压缩照跑照付钱然后照样停(`before 3112 → after 3112`)。
- 一次 goal 产生**两条 trace**(contract 段故意把 runId 改写成 `<runId>-contract`),
  按 runId 查不到 trace 差点被判定成"修复失败"。

**怎么抓**:凡是"缓存/复用一个昂贵的量"的地方,写下**它什么时候失效**,
并让失效的那一刻有代码表达(本仓用置位-消费的一次性标志,而不是长期开关)。

### S-6 · 判据把 A 读成了 B

**形状**:判据本身能跑、也会触发,但它测量的东西**不是**它名字说的那个东西。

**为什么没红灯**:它照常给出裁决,只是裁决是错的。

**本仓实例**
- **「在想」被读成「没反应」**(2026-08-01):停摆闸数的是 `text_delta`,
  而模型推理时发的是 `thinking_delta` —— 对它完全隐形。
  effort 提到 max 之后,一个正常思考 50 秒的叶子会被当成挂死杀掉。
- `filesTouched` 只收顶层 `args.path`,而 `hashline_edit` 的路径嵌在 patch 头里 →
  真交付的文件节点被产物闸全判 failed(恒空 = "谎报完工")。
- fan-in 前缀那条用例拿「节点甲」「节点乙」当数据,**两者共同的「节点」二字**把分叉点推后了 ——
  测试数据自带公共前缀,量到的是假的。

**怎么抓**:给判据写一条**反向用例**——"什么情况下它**不该**触发",
并确认那条用例真的不触发。只测"该触发时触发"的网,抓不到 A/B 错位。

### S-7 · 同一条规则散在多处,漏掉第三处

**形状**:同一个不变量在 N 个地方各实现一遍,修的时候只修了 N−1 处。

**为什么没红灯**:改过的那几处都对。

**本仓实例**
- 「sessionId 没串下去」一个 session 里出现**三次**:`runDagInternal` 自造 UUID ·
  `run-goal:193` 又解析一遍 · judge 调用不带 meta。
- 「三个调用点共用」的注释写着共用,实际**三缺一** —— 空转 BLOCKED 出口根本不写 journal。
- 同一个叶子在两条路上**两个寿命**:MCP 传 1h,TUI/sec-audit/review 不传 → 吃 240s 默认。
- **command 闸的环境事实只进了两份 prompt 里的一份**(2026-08-01):白名单/元字符/`expect_exit`
  写进了规划 prompt,**补丁重规划 prompt 一个字都没有** —— 而修复轮恰恰专门在改被判失败的验证节点。
  live 3/3 复现:它把 `expect_exit:1` 改写成 `grep …; rc=$?; test "$rc" -eq 1`(规划 prompt
  明文禁止的 shell 取反),把另一个改写成 `$(cat …)`,双双撞注入闸 → **假红**。
  当初把白名单塞进规划 prompt 的判据(「conductor 只能猜,猜错就是假红」)原样适用于这条路,
  只是当时没数一共有几处。收法同上:`commandGateRules()` 一份,两份 prompt 都拼它。

**怎么抓**:发现一处时**先数一共有几处**,再决定是修还是收成一处。
本仓的收法:`seats.ts`(座位)· `model-caps.ts`(模型能力)· `pi-transport`(唯一传输)。
> 两条路各写一份,早晚一份先漂 —— 而漂掉的那份就是下一个事故。

### S-8 · 归因归错了层

**形状**:观察到的现象是真的,但把它归给了错误的原因,于是**修错了地方**,或者**记下了一条错的事实**。

**为什么没红灯**:结论听起来完全合理。

**本仓实例**
- 探针报「10 分钟内按 runId 查不到 trace」→ 差点判定修复失败;
  实际是 contract 段**故意**改写了 runId(探错了 id)。
- **把 temp=0 不确定当成"温度被忽略"的证据**(2026-08-01):
  MoE 服务端在 temp=0 下本来就不确定(batch 路由)。重做成 `top_p=0.01` 硬夹才有分辨力。
- **把「思考模式的性质」登记成「模型的固有属性」**(2026-08-01):
  写成无条件的 `honorsSampling: false`,顺手抹掉了"关掉思考就能调温"这个真实存在的选择。

**怎么抓**:下结论前问一句 —— **这个观察还能被什么别的原因解释?**
把那个替代解释**排除掉**的实验设计出来,再下结论。
拒因说的是哪一层,别替它归因。

### S-9 · 前提在别的宿主上不成立 —— 同一段代码,寿命变了

**形状**:一个对象的正确性依赖它**活多久**,而活多久由**谁构造它**决定。
换一个宿主(短命 CLI → 长驻 daemon),前提悄悄翻面,**代码一个字都没改**。

**和已有几条哪里不一样**:S-3 是机制**没跑到**某条路上;这一条是机制**跑了**,
跑在一条它的前提不成立的路上。S-7 是同一条规则写了两份;这一条只有一份实现、一份注释,
注释里那句话在 A 路上是真的、在 B 路上是假的 —— **没有第二份可对照,所以没有"漂"可查**。

**为什么没红灯**:单测里 runner 现建现用,前提永远成立,测试**永远绿**;
生产上它退化成"返回上一次的结果",而上一次的结果**看起来完全正常**。

**本仓实例**(2026-08-01,live 抓到)—— command leaf 的确定性 memo 缓存。
它的安全论证有两环,**两环都被实测证伪**:

- ①「新调用 = 新 runner = 新缓存」是个**没人钉住的前提**:TUI/eval 每次现建 → 成立;
  MCP 是长驻进程,`assemble` 装配期建**一次** → 缓存跨了这台 daemon 上的**所有** run。
  实测:两个 runId 之间改掉盘上文件,第二跑仍返回旧值;同图对照组(命令串多一个空格 →
  缓存键不同)读到新值,排掉了"下游复述时幻觉"。
- ②「单 run 内输入文件不变 → 无 staleness」**在这台引擎上天然为假** —— 它的本职就是让
  agent 节点改文件。实测:同一张图里 `cat f` → agent 写 f → `cat f`(同一命令串)
  读回的是**写之前**的内容。第一版修复(按图清缓存)只堵了 ①,**② 原样还在**。

**危害方向是最坏的那个**:只缓存 `exitCode===0` ⇒ 红→绿看得见,**绿→红看不见** ——
一条 `bun test` 闸在这台 daemon 上过一次,之后代码改坏了也照绿。
它还顺手废掉了引擎那条设计(「command 节点刻意不落绿 checkpoint,resume 重跑一遍比跳过一个闸安全」):
重跑发生了,结果来自缓存,**闸还是被跳过了,只是降到没人看的一层**。

**结局:删掉,不留旋钮。** 先修后删,是因为**收益侧的读数是补做的** ——
留痕库全量 12 次真实 run / 25 个 command 节点,同一 run 内**重复命令串 = 0**(唯一一次重复
是升级轮为了测缓存自己造的,而它给出的正是错的答案)。它连设计时说的主场景都覆盖不了:
「兄弟节点跑同一条命令」是同层并发,缓存只在命令返回后写入,两个都 miss。
零命中 × 两条错误绿灯 ⇒ 这不是"修好边界"的事,是**它压根不该在**。

**怎么抓**:三条。
> ① 写"per-X 缓存/状态"时,把 **X 的边界交给知道边界的那一层**,别让它由构造位置隐式决定。
> ② 一个**只快不对**的机制,先量它**到底命中过几次**再谈修 —— 收益侧没有读数时,
>   人会本能地去修边界(我第一版就是),而正确的问题是"删掉它会损失什么"。
> ③ 缓存/复用类机制的测试必须**跨两次调用、且中间让世界变一次**:
>   单次调用的测试对这一族天生瞎,而"世界不会变"恰恰是它们最爱写的那个假设。

### S-10 · 判官是真的,喂给它的证据被沿途削掉了

**形状**:一道判定闸**确实在跑**、判据也写得对,而它看到的输入**被上游悄悄削掉了一块**。
于是它照着自己的判据给出裁决 —— 裁决是错的,但**推理是对的**,判词读起来完全合理。

**和已有几条哪里不一样**:S-1/S-2/S-3 说的是机制没跑或没接上;这一条**全接上了**。
S-6 是判据把 A 读成了 B(测错了东西);这一条判据没读错,是**东西根本没送到**。
要害在于:它的判词会把你引向"这个模型太严了 / 换个模型试试" —— 而真正该改的在上游三十行外。

**为什么没红灯**:每一段都自洽。命令跑了、退出码是 0、输出非空、节点 done、判词有理有据。

**本仓实例**(2026-08-01,一轮里撞到两次,都是被同一道闸的判词逼出来的)
- **`summarizeResults` 不给命令串与退出码**:终审看见一个裸的 `93`,不知道它是哪条命令跑出来的。
  它的判词逐字写着「未展示所执行的具体命令与退出码」—— 而这两样引擎手里都有
  (`plan.nodes[id].command` · `LeafResult.exitCode`)。补上之后同一条样本 0/3 → **3/3 判过**。
- **command leaf 的 `(stdout || stderr)` 二选一**:`bun test` 把版本横幅写 stdout、
  把 **`N pass / N fail` 汇总写 stderr** → 一个验证节点的全文输出只有 `bun test v1.3.14`。
  通过/失败数**从没进过** DAG、下游、终审或留痕库。而 conductor prompt 恰恰教它
  「把验证尾巴收成一个 `bun run tsc --noEmit && bun test` 节点」—— 最推荐的用法丢得最干净。

**怎么抓**:两条。
> ① **闸判不过时,先把它的判词当假设去查,再定谁错。** 本轮三次"它判错了"的初判**没有一次**
>   成立,而每次照判词去查都查出了真缺陷。判词是这一族唯一的免费探针 —— 它在替你描述
>   它看到的世界,而那个世界与你以为的不一样正是缺陷本身。
> ② 给闸写校准样本时,**把"喂进去的到底是什么"打印出来看一眼**。
>   `scripts/verifier-calib.ts` 末尾那行证据面自查(命令串在不在 / 退出码在不在)就是为此。

### S-11 · 消费者齐全,但整座岛没有入口

**形状**:一组文件互相 import,每个都有消费者,内部完全自洽 —— 而**这个闭包从生产入口到不了**。
它跟 S-1 不是一回事:S-1 是「声明了没人读」,这一条是「读的人都在,只是读的人自己也没人叫」。

**为什么没红灯**:tsc 只判类型,不判可达;测试跑得欢(测试是这座岛剩下的唯一访客);
所有"有没有人用"的 grep 都会命中 —— **岛内互相引用就足以让每一次单点查证通过**。
删掉入口的那次提交也不会红,因为被孤立的是**别处**的文件。

**本仓实例**(四次,没有一次是靠计划找到的,全靠人手工重算闭包)
- 砍 TUI 之后剩下的一批文件再没有入口(2026-08-01)。
- `skills/` 的函数级死码 —— 那次是按**符号**查出来的,不是按文件(2026-08-02)。
- 摘掉 `dream_consolidate` 工具 → `src/dream/` 四个文件当场成孤儿。
  连带效果:`dream` **座位**通过了「座位即承诺」闸(解析点确实在 `model-live.ts` 里),
  而那个文件没人调 —— **一条闸的绿建立在另一座孤岛上**(ADR-0003)。
- 删 `TaskSignals` 的连带:`plan/complexity.ts` 断了最后一个消费者。
  这一条是**上一个提交自己造的**,而且是在刚写完"要一个可达性工具"之后。

**怎么抓**:`src/harness/reachability.test.ts` —— 从 `cli.ts` + `scripts/*.ts` 走 import 图 BFS,
不可达的非测试 `.ts` 即红。**刻意不把测试当根**:只有自己的测试还在用的文件,在生产里就是死的,
应该红一次逼出显式决定。动态入口(按路径字符串 spawn / 外部脚本按路径参数跑)登记豁免并写明理由,
配反向闸防名单变垃圾桶。

**这道闸抓不到的**:① 只看静态 import,新增动态加载会误报(靠豁免名单兜);
② **不查函数级死码** —— 文件只要还有人 import 就算可达,哪怕一半导出没人用(上面第二条实例正是这层,
要按符号查)。别把它的绿读成"这个文件在生产里真的跑过"。

### S-12 · fail-open 吞掉的不是异常,是**证据**

**形状**:一处 `try { … } catch { /* 不该把一次真跑炸掉 */ }`。**这个判断通常是对的** ——
持久化失败不该杀死一次正在跑的活。但如果 catch 里**一个字都不留**,它同时销毁了
「这次降级过」这个事实,于是「成功了」与「失败了但我们决定继续」在事后**完全不可区分**。

它与 S-1 的区别:S-1 是机制没有消费者;这一条是**机制正确执行了它的降级路径,而降级本身不可观测**。

**为什么没红灯**:按设计它就不抛,所以任何"有没有异常"的检查都是绿的;
更麻烦的是**内存视图仍然自洽** —— 进程内每一次读都拿到"正确"的新状态,
只有另一个进程(或重启后的自己)才看得见分歧,而那时现场早没了。

**放大它的一条实现顺序**:

```ts
rec.status = to;        // ← 内存先改
this.persist(runId);    // ← 落盘在后, 且 catch 是空的
```

落盘是**持久真相**,内存只是缓存。先改缓存再写真相,一旦写失败,两边必然分歧,
而分歧的那一侧恰好是没人看的那一侧。

**本仓实例**(2026-08-02,一次 30 分钟的 live `dag_goal`)
- 症状:`goal-worker` 打印「终态 done」并 exit 0,而 `.omd/runs.db` 里那个 run
  **至今停在 `running`**,`updated_at` 停在起跑那一刻;同一次跑的 `dag-runs.db` **零行**。
- 两层 catch(`RunRegistry.persist` + `run-store.put`)**都一声不吭**,
  于是唯一能拿到的线索就是"两个库对不上",排查时无从下手。
- 排查代价:七个假设逐个证伪(改动本身 · SQL/schema · `process.exit` 丢 WAL ·
  `succeed` 不持久化 · 写错库 · worker 形状 · 引擎吞钩子异常),**触发原因至今未定位**
  —— 因为该留证据的那一刻什么都没留。
- ⚠ 原注释写着「记不下来最多是重启后少认得一个 runId」。**这句低估了代价**:
  对 detached run(无人值守跑完就走),盘上那条**就是唯一的出口**,
  丢了等于这次跑的结论没有任何人看得到。

**怎么抓**:没有通用闸(它是运行时条件,不是结构)。两条可执行的纪律:

> ① **每一个 fail-open 的吞点必须留一行**(runId / 状态 / 错误消息)。
>   吞掉异常可以,吞掉证据不行。「过了一道」与「过了两道」不是一回事,
>   同理「写成功了」与「写失败了但我们继续」也不是。
> ② **缓存与持久真相的更新顺序**:要么先落盘再改内存,要么在失败时把分歧**显式记下来**。
>   先改内存后落盘 + 空 catch = 保证分歧且保证无声。

**这条纪律抓不到的**:它只让下一次可诊断,**不解释这一次**。
本仓那次的触发原因仍是 `Unobserved`,不是 `Missing` —— 别把"装了灯"当成"修好了"。

## 怎么加一条

1. 确认它满足上面三条判据(尤其第 3 条:**两边都不报错**)。
2. 归到已有形态,或开一条新的 —— 新形态要说清**它和已有几条哪里不一样**。
3. 写实例时带上**当时的症状**(它伪装成了什么),那比缺陷本身更有复用价值。
4. **给出抓法。** 能自动化就落成测试并登记进上表;不能自动化就写成一条可执行的提问纪律。
5. 如果这一条是**自己犯的**,照写不误 —— S-8 的三条里有两条是。
